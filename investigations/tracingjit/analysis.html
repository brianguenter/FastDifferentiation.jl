Tracing Jacobians: results on 144 library functions, and how the cache works

A prototype differentiates ordinary Julia code containing data-dependent branches by recording the straight-line trace for one input, differentiating it with FastDifferentiation (FD), compiling the result, and reusing it for every later input that takes the same branches. This page reports what happened when it was run on a broad set of functions from registry packages, and describes the algorithm in full.

Summary

Of 144 test functions, produced a Jacobian that agreed with ForwardDiff (or with finite differences where ForwardDiff could not run the function), and none disagreed. Across those, a cached trace evaluated the Jacobian in a median of times less time than ForwardDiff.jacobian!. That excludes the one-time cost of recording, differentiating and compiling the trace, which had a median of seconds and a maximum of seconds on these functions. The 35 failures are missing methods for the Tracked number type, libraries that reject it, or problems in my test cases. None is a wrong answer.

Read the timings with these limits in mind. Timings were taken while up to four Julia processes ran in parallel on one machine, each case once, so ratios under about 2 times are not reliable. The ForwardDiff reference includes a small wrapper that reshapes the inputs and allocates the output, which the cached trace does not pay for. I chose the cases, they were not sampled, and they lean toward small problems (median 10 guards; largest Jacobian 16,771 nodes). The 35 failed cases are excluded from every speed figure.

What was run

Each case is a function from a package, called with deterministic random arguments. For each one the harness:

  1. runs the plain function on Float64 to confirm that it works;
  2. computes a reference Jacobian with ForwardDiff, or with 5-point central finite differences where ForwardDiff throws;
  3. calls the tracing Jacobian once (this records, differentiates, generates code and compiles) and compares with the reference using max |J − Jref| / max(|Jref|, 1). A case passes at 1e-6 against ForwardDiff or 1e-3 against finite differences;
  4. calls it on 8 inputs perturbed by about 0.1%, to see whether the trace is reused (a hit) or a new one is recorded (a miss);
  5. for some cases, calls it on inputs chosen to take other branches and checks those against the reference;
  6. times a cached call (eval_jacobian!, in place) against ForwardDiff.jacobian! with a preallocated config.

The 144 cases come from 21 packages, two of them standard libraries (LinearAlgebra, Statistics). Eleven more packages are installed and imported (Distributions, Geodesy, Rotations, StaticArrays and others) but have no cases yet.

Some failures were addressed after their run. The isless ambiguity fix was rerun for the DataInterpolations and BSplineKit cases, and all 10 now pass and are counted above. The rem and ldexp methods were added after the runs and have not been rerun, so Haversine and the polynomial-roots case still appear as failures. Speed of a cached trace

The cases with small gains are those where the trace is large and guards dominate: QuadGK integrals with hundreds of adaptive-subdivision comparisons, hcubature (1,384 guards) and the Brent root finder. Three cases ended in replay mode (the two QuadGK/hcubature cases with the most guards and the 3D hcubature polynomial), where a call runs f once on a cheap value-only number to read the branch decisions and then runs a guard-free Jacobian. The :auto mode chose that from its own timings.

Choices the prototype made

The algorithm

The prototype is one file, investigations/tracingjit/prototype.jl (module TracingPrototype), built on FD's graph API and a few internals. It does not read Julia's IR. Tracing runs the user's function on a number type that records what happens.

1. Tracked numbers

A Tracked value holds a Float64 (val) and an FD Node (node). Every arithmetic or elementary function computes both: the number for control flow and the node for the expression graph. The function receives its inputs as Tracked values whose nodes are FD variables. Generic code such as A \ b, sort or quadgk runs unchanged because Tracked is a Real and implements the numeric interface those functions use (comparisons, floor, round, mod, rem, sign, copysign, isnan, eps, typemax and so on).

2. Guards: the record of branch decisions

A comparison such as a < b on tracked numbers returns an ordinary Bool computed from the values, so Julia's if, while, &&, sort and max work as usual. It also builds the node for the comparison and records a guard: the pair (comparison node, observed outcome). The resulting trace contains no branches because the run took exactly one path. It is valid for every input that makes all recorded comparisons come out the same way.

Functions that need an actual integer (Int(x), floor(Int, x), indexing with a computed value, round, ceil, exponent) are concretized. The integer is taken from the value, and guards are recorded saying that the node still lies in the same integer interval, such as k ≤ x < k+1. mod is kept as its own node with derivative rules (d/dx = 1, d/dy = −(x − mod(x,y))/y), so a guard on Int(mod(u,4)) holds for u = 1, 5, 9, ….

3. Differentiate the trace

The outputs are a vector of nodes. The prototype computes the Jacobian in two ways and keeps the one with fewer operations: FD's reverse-mode rows (reverse_AD) and FD's factoring Jacobian (FD.jacobian). Factoring is only tried when the trace has at most 20,000 nodes. Reverse rows were added after measurements showed that on large traces from iterative algorithms the factoring Jacobian came out 2 to 10 times larger and took far longer to compile. Why FD's factoring did worse there is not resolved (see the open questions).

4. Generate code

FD's code generator turns the Jacobian graph into straight-line statements that write into a preallocated result matrix (in_place) and return true or false, or return a matrix or nothing when not in place. Traces above 30,000 statements are split into chunks of 10,000, each compiled as its own function over a shared workspace vector (booleans are stored as 1.0 and 0.0). A hard cap (MAX_STATEMENTS) refuses traces too large to compile.

5. The cache

A TracingJacobian keeps a vector of traces, most recently used first, bounded by max_traces; the least recently used is evicted. Each Trace holds its generated function, its statistics, the recorded decisions as a bit vector and an integer vector, a 64-bit signature, and (in compiled mode) the guard list. A call goes one of two ways, depending on the guard mode.

Compiled mode

Each trace's function evaluates its own guards before computing anything. The generated code has statements of the form v || return false with the expected outcome baked in. The cache tries traces in most-recently-used order, and the first one that does not return false has written the Jacobian. If every trace rejects, f is recorded again as a new trace. The cost of a call is one fused call for the hit plus the guard evaluation of each trace rejected first.

Replay mode

Run f once on Probe numbers, which carry only a Float64. Every comparison and integer conversion appends its result to a DecisionLog: a preallocated 2048-bit BitVector plus a 256-entry integer vector, addressed with a counter and doubled when full. No exceptions are used. The log is hashed to a 64-bit signature, and the matching trace is found by signature plus an exact word comparison. The guard-free Jacobian is then called. The call pays one run of f on plain floats instead of evaluating many guard expressions, which helps when there are many guards or many cached traces.

6. Choosing the mode automatically

In :auto mode (the default) the cache starts in compiled mode. After each recording it times the fused call, a replay lookup and a rejection, and estimates the per-call cost of each mode. Replay is estimated as the probe run plus (the share of statements that are not guards) × the fused call time. Compiled is the fused call time plus (traces − 1)/2 × the rejection time. If replay is estimated cheaper, the cache switches once, and each trace regenerates its guard-free function the first time it is used in replay mode. An earlier version of this estimate assumed that the Jacobian was half of the fused call and wrongly switched determinants, Cholesky and SVD to replay. It now uses the measured statement counts.

function (tj::TracingJacobian)(result, args...)
    x = flatten(args)
    if tj.active == :compiled
        for tr in tj.traces                       # most recently used first
            tr.fn(result, x) && return touch!(tj, tr)      # guards pass, Jacobian written
        end
    else                                          # :replay
        sig, bits, ints = run_probe(f, args)       # one run of f on Probe numbers
        tr = lookup(tj.traces, sig, bits, ints)    # hash, then exact word comparison
        tr !== nothing && return (tr.free(result, x); touch!(tj, tr))
    end
    tr = record!(tj, args, x)                     # miss: run f on Tracked numbers,
    insert!(tj.traces, 1, tr)                     #   differentiate, generate, compile
    evict_oldest!(tj)                             #   keep at most max_traces
    maybe_switch!(tj)                             # the :auto decision
    tr.fn(result, x)
end

7. When the answer can be wrong, and when the prototype cannot run

  • Validity is per path. A cached trace gives the derivative of the path actually taken. At a branch boundary (equality in a comparison, a tie in max) the derivative is not defined, and the result follows whichever side was recorded.
  • Impure or external state. If the function reads global state, random numbers, the clock or a file, the guards cannot see it, and the trace freezes whatever happened during recording. Nothing detects this.
  • Type constraints. Code that insists on Float64 or AbstractFloat, calls C or LAPACK on the input type, or needs a feature that Tracked lacks fails at trace time with a MethodError. That is the cause of most failures in the table above.
  • Size. Compile time, not run time, limits large traces. A loop that runs for hundreds of iterations becomes hundreds of unrolled steps, and each distinct trip count is a separate trace.
  • Constants in comparisons. Every comparison, including one between two constants, writes a bit to the replay log, so the log from the recording run lines up with the log from a replay run.

Open questions and work not done

  • FD against reverse mode. I expected FD's factoring to match or beat reverse differentiation, but on the SVD traces it came out several times larger. The cause is unresolved. A graph with a wide bottleneck is one suspect and a mistake in how I call FD is another.
  • Timings under load. Rerun the suite on an idle machine, with several repeats, before quoting any ratio under about 3×.
  • Failure fixes. Add Tracked methods for the Bessels and SpecialFunctions internals. Fix the Optim and TaylorIntegration test cases, which fail on plain Float64. Look at NaNMath, Krylov and Tsit5, which reject the number type. Rerun the cases changed since their last run.
  • More cases. Program-like functions (a bouncing ball, saturating controllers, tax brackets, power iteration, golden-section search) and packages such as Distributions, Rotations, StaticArrays and Quaternions are installed but not yet written as cases.
  • Ideas not yet tried. An interpreter tier for traces used only a few times, compiling after N uses. A packed 64-bit logging path for replay. A dictionary on the signature for large caches. Sharing one compiled trace between structurally identical traces. A 10×10 SVD with reverse rows and chunking.
